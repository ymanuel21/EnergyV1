# EBT Plaza — English Localization: Implementation Record

Phase 2 (implementation) and Phase 3 (English-only behaviour) record.
Companion documents: `ENGLISH_LOCALIZATION_AUDIT.md` (Phase 1 inventory, repository root) and
`TRANSLATION_BRIEF.md` (term base + translation rules).

## 1. Shape of the change

There are exactly two moving parts, and each reverses independently.

| Part | What it is | Where | How to reverse |
| --- | --- | --- | --- |
| **Content overlay** | English copy for database rows, merged over rows on the public read path | `src/lib/i18n/` | Delete the directory and the `applyEn*` calls. **The database was never written to**, so the site returns to its previous state exactly. |
| **Code copy** | Indonesian strings in components, pages, metadata and fallback datasets, translated in place | `src/**` | `git revert` the localization commits. |

Nothing else changed: no routes, no URL slugs, no layout, no CSS, no images, no business logic,
no API contract, no admin behaviour.

## 2. Why an overlay instead of editing the database

`ebtplaza.com` reads its catalogue from Neon Postgres, and the same tables back the admin CMS. Writing
English into the database would have two bad consequences:

1. the original Indonesian copy would be destroyed, making reversal impossible; and
2. admin staff would open edit forms containing English text generated by us, and could save it back
   over the live Indonesian content.

So the database keeps its Indonesian values untouched, and English is applied when rows are read for
the public site. Admin screens call none of these helpers and continue to show Indonesian.

`getPublicHomepageSections`, `getAllProducts`, `getProductBySlug`, `getProductsByCategory`,
`getProductsPaginated`, `getAllCategories`, `getCategoryBySlug`, `getAllArticles`, `getArticleBySlug`,
`getAllFaqs`, `getPublicNavigationLinks`, `getAllPages`, `getPageBySlug` and `getSiteSettings` are the
hooked read paths.

## 3. How the overlay resolves a row

* **Keying.** Rows are matched by slug first, then by id (`products`, `categories`, …), by id for
  `faqs`/`testimonials`/`navigation_links`/`homepage_sections`, and by `key` for `settings`.
* **Strings** are replaced only when the row already holds a string, so a translation can never
  materialise a column the row never had.
* **JSON columns** (a homepage section's `settings`) are *merged*: only the translated keys are
  overridden, so image paths, anchor ids, accent colours, sort orders and linked ids survive.
* **List columns** (a project's `highlights`) are replaced wholesale.
* **An unmatched row passes through unchanged** — a gap degrades to "still Indonesian", never to a
  blank string.

### Product specifications

Spec tables are a normalised structure — `{category, key, label, value}` — and the vocabulary repeats
across products ("Cooling" appears in 69 rows, "Operating Temperature" in 95). Rather than duplicate
spec text per product, `src/lib/i18n/data/spec-terms.en.json` holds one dictionary per field
(42 categories, 211 keys, 344 values) which `applyEnSpecifications` maps over every product's spec
array. That covers 3,088 spec rows from 597 dictionary entries.

## 4. Coverage

| Content | Volume | How |
| --- | --- | --- |
| Product descriptions | 99 spec sheets, 183,124 chars | Translated to `products.en.json` |
| Product spec tables | 3,088 rows / 230 products | `spec-terms.en.json` dictionaries |
| Product names / warranties | 10 names, 4 warranty labels | `products.en.json` patches |
| Pages, articles, FAQs, categories, projects, testimonials, navigation, settings, homepage sections | 106 rows | `content.en.json` |
| Code copy | ~350 values across 82 source files (735 insertions / 690 deletions — almost all single-line string swaps) | `docs/i18n/code-copy.en.json` applied by `scripts/apply-code-copy.py` |
| Fallback datasets (`src/lib/data/*`) | Products, categories, articles, pages | Translated in place |

Spec dictionaries: 42 categories, 211 keys, 348 values — 601 entries covering 3,088 spec rows, i.e.
each translated string is reused about five times.

Public read paths hooked: `src/lib/api/*` (products, categories, articles, faq, navigation,
homepage-sections, static-pages, site-settings), `src/lib/site-server.ts` (site settings cache),
`src/lib/repositories/project.ts`, `src/lib/repositories/index.ts` (projects, testimonials,
navigation, homepage sections) and `src/app/testimoni/page.tsx`.

**Left in Indonesian on purpose:** the whole admin CMS (`src/app/admin/**`,
`src/components/admin/**`), dev scripts (`src/scripts/**`), the new-page templates in
`src/lib/static-page-templates.ts` and the admin module registry — all internal tools used by
Indonesian-speaking staff, none of them customer-facing. `quote_requests.message`/`.notes` hold real
customer submissions and are never rewritten.

## 5. Decisions taken, and why

1. **URL slugs stay Indonesian.** Renaming them would break every indexed URL and internal link. The
   brief requires routes to be preserved; routes are structure, the copy inside them is what changed.
2. **Numerals are reproduced character for character**, including Indonesian separators
   ("5,12 kWh" stays "5,12 kWh", "Rp 1.444/kWh" stays "Rp 1.444/kWh"). No figure is ever re-formatted,
   rounded or converted, so no factual claim can drift. See §6.
3. **`PLTS`, `PLN` and brand names are retained.** `PLTS` (pembangkit listrik tenaga surya) is the
   site's own product-naming term — "PLTS Packages", "PLTS System Types" — while prose uses "solar
   power system".
4. **Honorifics are localized.** "Ibu Ratna" → "Mrs. Ratna", "Pak Dodi" → "Mr. Dodi",
   "Kepsek Supriyadi" → "Principal Supriyadi". The names themselves are untouched.
5. **Testimonial `role`/`company` values are translated** ("Pemilik" → "Owner", "Gudang Logistik" →
   "Logistics Warehouse"); institutions that are proper nouns (SMK Negeri 3, Masjid Al-Hidayah,
   Pemkab Garut, Dinas PU Makassar, PT …) are left as written.
6. **No language switcher exists to remove.** The site had no i18n library, no locale routing and no
   switcher, so Phase 3's "remove or hide language controls" is satisfied trivially. Nothing was
   deleted that the client may later want.
7. **No browser-language redirect** was added, so no visitor can be bounced back to Indonesian.

## 6. For client review before launch

* **Number formatting is unchanged** (decision 2 above). If the client prefers English conventions
  ("5.12 kWh", "Rp 1,444/kWh"), that is a follow-up pass over the dictionary files — say the word and
  it can be done without touching the database.
* **Testimonials** are translated faithfully and attributions localized (decision 4/5). The client
  should confirm the wording and the honorifics.
* **Legal pages** — Terms & Conditions, Privacy Policy, Return Policy, Shipping Policy — are
  translated accurately but are not legal advice; a qualified reviewer should sign them off.
* **Addresses** keep street and district names; only administrative words are translated
  ("Kecamatan Penjaringan" → "Penjaringan District", "Jkt Utara" → "North Jakarta").
* Two pre-existing content inconsistencies were found and left alone (they are data, not translation):
  the `settings.address` row is a Jakarta address while `src/lib/site.ts` defaults to a Bandung one,
  and the DB `tentang-kami` page address does not match the `settings.address` row.

## 7. Verifying

```bash
npx tsc -p tsconfig.json --noEmit     # typecheck
npm run build                         # production build
python3 scripts/apply-code-copy.py --residue   # Indonesian left in customer-facing source
npx playwright test tests/e2e/localization     # crawls every public route, fails on Indonesian
```

The Playwright suite loads each public route, reads the rendered text and fails listing any
Indonesian word it finds, so a future hardcoded label or untranslated CMS field is caught immediately.
